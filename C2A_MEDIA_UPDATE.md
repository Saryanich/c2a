# C2A — план обновления передачи файлов

Статус: спецификация согласованных изменений. Текущая реализация приложения находится в одном файле `index.html`; этот документ описывает целевое поведение перед изменением рабочего кода.

## 1. Новая структура интерфейса

Убрать четыре раздельные вкладки `Audio → Code`, `Code → Audio`, `Text to Code`, `Code to Text`. Оставить две универсальные вкладки:

### File to Code
Передача в формат C2A с последующим восстановлением исходного файла:
- текст;
- фотографии;
- аудио.

### File to Audio
Кодирование данных в WAV для передачи звуковым сигналом:
- текст;
- фотографии.

Внутри вкладки тип содержимого определяется выбранным файлом или вводом текста. Не создавать отдельную верхнюю вкладку и отдельные основные кнопки для каждого типа. Действия загрузки, запуска, остановки, сохранения и приёма должны быть контекстными и общими.

Видео в этот объём работ не входит.

## 2. Фото: качество и восстановление

- Поддерживать передачу фотографий в обоих направлениях: File to Code и File to Audio.
- Сохранять исходные размеры изображения и цветовые данные.
- Не увеличивать разрешение, резкость или детализацию искусственно.
- Не создавать результат, который заявляется как более качественный, чем оригинал.
- При возможности использовать обратимое (lossless) кодирование, чтобы восстановить исходные пиксели без изменений.
- Если для передачи по аудио необходим компромисс по размеру или скорости, явно показывать выбранный режим и фактические параметры. Не выдавать сжатую копию за побитово идентичный оригинал.
- Не увеличивать файл без необходимости; показывать исходный размер, размер пакета/потока, коэффициент и результат проверки.
- Для форматов с особенностями декодирования (например, HEIC/HEIF, GIF, TIFF) проверять поддержку отдельно; неподдерживаемый формат не должен молча портиться.

## 3. Live-приём через микрофон (диктофон)

Live — это режим приёма звуковой передачи через микрофон, а не трансляция с камеры.

Во время приёма интерфейс непрерывно показывает уже восстановленную часть данных:

### Фото
- Создать холст с исходными шириной и высотой после получения заголовка.
- По мере приёма и проверки блоков обновлять соответствующие пиксели/области изображения.
- Ещё не принятые области визуально отличать от восстановленных.
- Не ждать окончания передачи, чтобы впервые показать изображение.
- При повторном получении или исправлении повреждённого блока обновлять соответствующую область.

### Текст
- Показывать уже принятые и декодированные символы по мере поступления.
- Не выводить неподтверждённые/повреждённые символы как достоверный результат; при необходимости отмечать ожидающие проверки данные.
- После завершения показывать итоговый текст и результат проверки целостности.

### Общие требования
- Отображение Live не должно блокировать приём и декодирование.
- Обновлять интерфейс порциями, а не перерисовывать его на каждый аудиосэмпл.
- Показывать отдельно уровень входящего звука, найденную синхронизацию, долю принятых полезных данных, ошибки и контрольную сумму.
- При потере сигнала сохранять уже принятые данные и продолжать приём после восстановления сигнала, если протокол позволяет.

## 4. Чувствительность и надёжность аудиоприёма

Текущая проблема: при громкости ноутбука около 60% и расположении динамика рядом с микрофоном интерфейс показывал лишь около 5% приёма. Исправить именно тракт захвата и декодирования, а не просто визуальную шкалу.

Требования:
- Измерять и показывать реальный уровень входа (RMS и peak) отдельно от процента успешно декодированных данных.
- Реализовать устойчивую автоматическую регулировку усиления (AGC) с ограничением усиления, защитой от клиппинга и плавным изменением gain.
- Использовать адаптивный порог обнаружения сигнала и оценку шумового фона.
- Проверить работу с тихим сигналом, разной громкостью, расстоянием и фоновым шумом.
- Не включать шумоподавление/эхоподавление без проверки: браузерные фильтры могут вырезать полезные частоты FSK. Дать декодеру максимально чистый исходный сигнал и при необходимости сравнить режимы захвата.
- Улучшить синхронизацию, временную/частотную устойчивость и обработку ошибок; не снижать строгость CRC ради искусственного увеличения процента.
- Не считать усиление программой заменой физически отсутствующему сигналу: показывать понятную диагностику, если микрофон действительно не слышит передачу.

### Найденная проблема в текущем Live-декодере

В `index.html` `liveState.pcm` инициализируется как обычный массив `[]`, данные добавляются через `push(...norm)`, но затем код вызывает у него `.subarray()`. У обычного JavaScript Array метода `.subarray()` нет. Это может ломать обработку входящих аудиоблоков. Переработать PCM-буфер на согласованный тип (например, Float32Array с управляемым накоплением/кольцевым буфером) и проверить индексы при удалении старых данных, чтобы обработка не теряла или не повторяла биты.

Также проверить, что `lastProcessedSamples`, позиции битов и `rawBits` остаются согласованными после очистки/ограничения буфера. Текущий AGC и шкала уровня не должны путать амплитуду звука с процентом успешно принятых данных.

## 5. Протокол и целостность

- Использовать единый контейнер/заголовок для текста и изображений в обоих способах передачи.
- В заголовке хранить тип содержимого, длину, параметры изображения (ширина, высота, формат/режим кодирования) и идентификатор передачи.
- Передавать данные блоками с порядковыми номерами и контрольными суммами.
- Для повреждённых блоков предусмотреть обнаружение ошибок и, где возможно, повтор/восстановление; не подтверждать блок до проверки.
- Сохранять совместимость с уже созданными C2A-файлами и текущей схемой текстового FSK, насколько это возможно. Изменение формата сопровождать версией и явной проверкой старых файлов.

## 6. Сохранение существующей функциональности

- Не ломать существующее кодирование и декодирование аудио в C2A.
- Сохранить текущую логику проверки размера C2A относительно исходного аудиофайла; новые типы файлов должны иметь собственные корректные критерии размера и качества.
- Не смешивать аудиофайл как исходный файл для File to Code с WAV-сигналом как транспортом File to Audio.
- Не добавлять передачу видео в рамках этой задачи.

## 7. Проверки готовности

1. Текст проходит File to Code: кодирование → декодирование → точное совпадение исходного текста.
2. Текст проходит File to Audio: WAV → воспроизведение через динамик → Live-приём микрофоном → точное совпадение и успешная CRC.
3. Фото проходит File to Code: восстановленные размеры и пиксели совпадают с оригиналом в lossless-режиме.
4. Фото проходит File to Audio: во время воспроизведения Live-окно постепенно заполняется принятыми пикселями; после завершения проверяется целостность.
5. Проверить маленькие и большие изображения, разные пропорции, прозрачность и поддерживаемые форматы.
6. Проверить тихий сигнал, среднюю и высокую громкость, разные расстояния, фоновые шумы и разные устройства ввода.
7. Отдельно проверить отсутствие зависаний интерфейса и чрезмерного расхода памяти на больших файлах.
8. Проверить, что уровень микрофона, прогресс полезных данных и процент CRC/ошибок отображаются независимо и правдиво.

## 8. Порядок реализации

1. Исправить и протестировать текущий микрофонный тракт и буфер Live-приёма.
2. Выделить общий контейнер и блоковую передачу текста/фото.
3. Добавить фото в File to Code с точным lossless-восстановлением.
4. Добавить фото в File to Audio и Live-отрисовку по принятым блокам.
5. Объединить существующие функции в две вкладки File to Code и File to Audio.
6. Провести проверки из раздела 7 и только после них считать функции готовыми.

Главный принцип: достоверное восстановление данных важнее красивого процента прогресса. Интерфейс должен показывать только реально принятые и проверенные данные.
